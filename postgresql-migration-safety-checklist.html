PostgreSQL Migration Safety Checklist Before Production

Technical education for teams preparing a production migration. This is not a safety guarantee or a substitute for staging validation and qualified human review.

1. Separate compatibility changes from destructive changes

Start by classifying every migration file:

  • Expand: add nullable columns, new tables, new indexes or backward-compatible functions.
  • Migrate: backfill data, dual-write, reconcile old and new representations.
  • Contract: add stricter constraints, stop old readers/writers and remove legacy objects.
  • Destructive: DROP TABLE, DROP COLUMN, TRUNCATE, or unqualified DELETE/UPDATE.

A single release containing all four categories is difficult to roll back and difficult to observe. Expand first. Backfill separately. Constrain after the data is proven valid. Remove legacy objects only after a compatibility window.

2. Check old and new application versions

During a rolling deployment, both application versions may run at the same time.

Ask:

  • Can the old application run against the expanded schema?
  • Can the new application run before the backfill is complete?
  • Does the new code write both old and new representations during transition?
  • Will a rollback leave rows that the old application cannot understand?
  • Do background jobs, reports, exports or integrations read the affected objects?

A column rename can look trivial in SQL while breaking every old process that still uses the previous name.

3. Classify lock and rewrite risk

Migration review must account for table size and traffic.

Questions to answer:

  • Will this operation scan or rewrite the table?
  • Which lock does it acquire?
  • Which reads and writes does that lock block?
  • What are the lock timeout and statement timeout?
  • How long did the operation take on production-like data?
  • Can a waiting migration block later queries behind it?

Do not approve a migration from an empty staging database. A fast operation on 1,000 rows may behave very differently on a table with 10 million rows.

PostgreSQL's ALTER TABLE documentation and explicit locking documentation describe the relevant lock behavior. The exact impact still depends on the operation, PostgreSQL version, data volume and deployment context.

4. Build indexes outside transaction wrappers

CREATE INDEX CONCURRENTLY can reduce write blocking, but PostgreSQL does not allow it inside a transaction block. Migration frameworks sometimes wrap a migration in a transaction automatically.

Check:

  • Does the runner wrap this file in BEGIN and COMMIT?
  • Can this migration be marked non-transactional?
  • Is the index valid after the build?
  • What happens if the build is interrupted?

PostgreSQL's CREATE INDEX documentation explicitly notes that a regular index build can run inside a transaction block, while a concurrent build cannot.

A text scanner may see the SQL but not the framework's transaction behavior. That requires runner-specific review.

5. Add constraints in the safest order

For existing tables, separate adding a constraint from validating it.

For a foreign key or CHECK constraint:

  1. Add the constraint as NOT VALID.
  2. Verify and reconcile existing data.
  3. Validate the constraint in a separate controlled migration.
  4. Monitor locks and errors while validation runs.

PostgreSQL's ALTER TABLE documentation describes NOT VALID and VALIDATE CONSTRAINT as tools for improving concurrency when a table may contain pre-existing violations.

For NOT NULL:

  • first prove that no rows contain NULL;
  • consider a validated NOT VALID not-null check on versions that support it;
  • set NOT NULL only after the preconditions are evidenced;
  • account for the scan and lock behavior of the exact PostgreSQL version.

6. Design the backfill as an operational job

Do not treat a backfill as one large UPDATE merely because it has a WHERE clause.

The backfill plan should include:

  • stable key ranges or another deterministic pagination strategy;
  • bounded batch size;
  • commit per batch;
  • idempotent retry behavior;
  • progress checkpoints;
  • processed, skipped and failed row counts;
  • reconciliation against the source of truth;
  • lock duration, replication lag and storage monitoring.

Also decide what happens if an application write changes the row while the backfill is running. Dual-write, database triggers, queues or carefully ordered batch jobs may be appropriate, but each choice changes the failure modes.

7. Distinguish backup existence from recoverability

“We have daily backups” is not enough.

Before approving a destructive or difficult-to-reverse step, verify:

  • retention period;
  • restore time objective;
  • point-in-time recovery availability;
  • who can authorize a restore;
  • whether the restore has been tested recently;
  • whether the application can tolerate the data loss implied by recovery.

A reverse migration cannot reconstruct a dropped column or table unless the data was exported or otherwise preserved.

8. Choose rollback or forward-fix before deployment

Every risky migration should have a stop condition and a response plan.

Examples:

  • invalid concurrent index;
  • unexpected lock duration;
  • replication lag above threshold;
  • constraint validation failure;
  • increasing application error rate;
  • data-quality mismatch.

For each condition, define whether the team will:

  • stop the release;
  • revert application code;
  • drop or defer a constraint;
  • continue forward with a narrower fix;
  • restore from backup.

“Rollback” is not a complete answer unless the team knows exactly what can and cannot be reversed.

9. Rehearse with production-like data

Use representative row counts, index sizes and concurrency where possible.

The rehearsal should test:

  • old and new application versions;
  • migration runner transaction behavior;
  • lock timeout and statement timeout;
  • one successful and one failed backfill batch;
  • constraint validation with invalid and valid data sets;
  • query plans for affected queries;
  • storage headroom;
  • replication lag;
  • the final stop or rollback procedure.

The goal is not to prove that nothing can fail. The goal is to learn how the system fails before production does.

10. Record evidence, not opinions

Create an evidence table:

This is where an AI-generated migration review becomes useful. A tool can flag a pattern. A human reviewer has to distinguish:

  • what the files prove;
  • what the configuration suggests;
  • what was demonstrated only in a development or replica environment;
  • what remains blocked or unverified.

A practical go/no-go summary

Use this decision structure:

  • Go: every critical item has evidence and the rollout gates are satisfied.
  • Conditional go: only backward-compatible expand steps run now; later phases have separate gates.
  • No-go: destructive cleanup, invalid data assumptions or recovery prerequisites remain unresolved.

For most multi-phase schema changes, “conditional go for the expand phase” is more realistic than approving the entire migration set at once.

What a static scanner cannot tell you

A file-only scanner can detect visible patterns such as:

  • destructive DDL;
  • non-concurrent indexes;
  • CREATE INDEX CONCURRENTLY inside an explicit transaction;
  • constraints added without NOT VALID;
  • unqualified UPDATE or DELETE;
  • potentially volatile defaults.

It cannot determine:

  • actual table size or lock duration;
  • query plans;
  • application compatibility;
  • whether a runner adds its own transaction;
  • data-quality distribution;
  • backup integrity or restore success;
  • production traffic;
  • whether a later cleanup object is still used.

That limitation should be visible in the report. A review that says “the scanner found nothing” is not a release approval.

Final checklist

  • Migration files are classified by expand, migrate, contract and destructive phases.
  • Old and new application versions were checked.
  • Lock and rewrite risks were evaluated against production-like data.
  • Concurrent index creation is outside transaction wrappers.
  • Existing-row constraints use an appropriate add/validate sequence.
  • Backfill is bounded, idempotent and reconciled.
  • Backup and restore evidence exists.
  • Stop conditions and rollback/forward-fix steps are documented.
  • The rollout was rehearsed with representative data.
  • Every material claim has a visible evidence state.

If several boxes are still unknown, the safer release decision is usually to split the migration rather than approve the whole bundle.
