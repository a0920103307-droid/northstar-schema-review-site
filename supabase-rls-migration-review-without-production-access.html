Supabase evidence guide

Supabase RLS Migration Review Without Production Access

Technical education for teams preparing a production migration. This is not a safety guarantee or a substitute for staging validation and qualified human review.

What RLS actually depends on

Row Level Security is not a single toggle. The effective access decision can depend on:

  1. Which schema is exposed through the Data API.
  2. Which roles have object and function grants.
  3. Whether RLS is enabled on each exposed table.
  4. Which policies exist for SELECT, INSERT, UPDATE and DELETE.
  5. How tenant, user and organization identity is derived.
  6. Whether a policy uses trusted claims or user-editable metadata.
  7. Whether SECURITY DEFINER functions safely control search path and execution rights.
  8. Whether Storage and Edge Functions enforce equivalent rules.
  9. Which database role the deployed application actually uses.
  10. Whether tests exercise both allowed and denied access paths.

Supabase's Row Level Security guide and production security checklist are useful starting points. A migration review still has to connect those recommendations to this application's actual schema and roles.

1. Confirm the exposed schemas and grants

Start with the API boundary.

Request evidence that shows:

  • exposed schemas;
  • table and sequence grants for each client-facing role;
  • function grants;
  • whether anon, authenticated or another role has broader access than intended;
  • whether administrative schemas are excluded from the API.

Do not infer that a table is private merely because the frontend does not display it. The API boundary is determined by database privileges, schema exposure and policy behavior.

2. Verify RLS is enabled on every relevant table

One missing ENABLE ROW LEVEL SECURITY can change the result.

The review should distinguish:

  • RLS enabled with a policy;
  • RLS enabled with no policy;
  • RLS disabled;
  • RLS enabled but bypassed by the role used by a function or service.

Supabase's advisor documentation includes dedicated checks such as RLS disabled in a public schema and RLS enabled without policies. See the Supabase advisors guide.

3. Review policy coverage by operation

A policy for SELECT does not automatically provide a safe UPDATE policy, and a policy that restricts tenant visibility does not automatically protect function execution or Storage.

For each table, verify:

  • read policy;
  • insert policy;
  • update policy;
  • delete policy;
  • USING expression;
  • WITH CHECK expression;
  • whether the role can bypass RLS.

An UPDATE policy with a restrictive USING clause but a weak WITH CHECK clause may allow a row to move into a tenant the user should not control.

4. Trace identity to a trusted source

Policies commonly use an authenticated user ID, organization membership table or JWT claim.

Ask:

  • Can the user edit the value used for authorization?
  • Is user metadata being treated as an authorization source?
  • Does organization membership come from a protected table?
  • Does a stale or missing membership fail closed?
  • Can one user create a membership for another tenant?
  • Is service-role access kept outside client paths?

Supabase explicitly warns that some user metadata can be updated by the authenticated user. Authorization should not rely on a field the user can change.

5. Review SECURITY DEFINER functions

A policy can be correct while an exposed function bypasses it.

For every security-definer function, request:

  • owner;
  • SECURITY DEFINER status;
  • explicit or trusted search_path;
  • execute grants;
  • input validation;
  • tenant checks;
  • whether the function returns rows from multiple tenants;
  • whether the function can perform writes that the caller could not perform directly.

The Supabase advisor set includes checks for mutable function search paths and anonymously or authenticated-executable security-definer functions. That is evidence of why function review belongs in the same scope as RLS policy review.

6. Treat Storage policies as a separate authorization surface

Database table policies do not automatically secure Storage objects.

Review:

  • bucket visibility;
  • object path convention;
  • tenant and user ownership encoded in the path;
  • select/upload/update/delete policies;
  • public versus private bucket choice;
  • whether a user can list another tenant's folder;
  • whether replacing an object can bypass an upload policy.

If Storage is in scope, request its policy SQL and sanitized configuration evidence. Do not mark storage access as verified from table policies alone.

7. Review policy performance with representative scale

A policy can be secure and still be a performance problem.

Questions:

  • Are columns used in policy predicates indexed?
  • Does the policy evaluate stable auth context efficiently?
  • Does a nested membership lookup run once or per row?
  • Are multiple permissive policies combined in a way that causes repeated work?
  • Is the issue demonstrated in a production-like dataset or inferred from policy text?

Supabase documents RLS performance practices and advisor checks for issues such as missing indexes. Performance conclusions should still be labelled Configured, Replica-only or Unverified until tested at representative scale.

8. Test both allow and deny

A policy that allows the correct user path is not enough.

The test matrix should include:

  • user in the correct tenant;
  • authenticated user in another tenant;
  • user with no membership;
  • anonymous request;
  • stale membership;
  • service-role path;
  • storage access;
  • security-definer function;
  • update that attempts to change tenant ownership;
  • insert with a forged tenant identifier.

The deliverable should record which tests were executed and which remain blocked.

9. Do not confuse RLS with complete application security

RLS protects row access in PostgreSQL. It does not automatically address:

  • secrets in client code;
  • overly broad API keys;
  • unsafe Edge Function authorization;
  • payment logic;
  • file upload malware;
  • CSRF or browser security;
  • backup access;
  • production role drift;
  • a penetration-test finding.

A narrow RLS review should state these exclusions clearly rather than imply complete platform security.

This evidence discipline is more useful than a binary “secure” or “insecure” label.

What a file-only review can deliver

  • an inventory of tables, policies and grants supplied;
  • a gap analysis by operation and role;
  • policy and function patterns that require attention;
  • a deny-path test matrix;
  • a distinction between confirmed, configured, replica-only and unverified claims;
  • prioritized remediation questions;
  • a go/no-go or conditional-go decision for the reviewed scope.

It cannot deliver a penetration-test certificate, guarantee tenant isolation, inspect live production sessions or prove that no dashboard drift exists.

Final checklist

  • Exposed schemas and grants are known.
  • RLS status is known for every in-scope table.
  • Every client operation has an intended policy path.
  • Authorization identity comes from a trusted source.
  • SECURITY DEFINER functions are reviewed.
  • Storage and Edge Function boundaries are either reviewed or explicitly excluded.
  • Policy columns have a performance review.
  • Allow and deny cases are tested.
  • Functional and non-functional claims have an evidence state.
  • Production role and runtime behavior are marked unverified until evidenced.

The safest conclusion is often narrower than the buyer expects: what the supplied artifacts prove, what they merely configure, and what still needs a controlled runtime test.
