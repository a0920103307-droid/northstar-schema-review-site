Prisma deployment guide

Prisma-Generated PostgreSQL Migration Risks

Technical education for teams preparing a production migration. This is not a safety guarantee or a substitute for staging validation and qualified human review.

1. Review generated SQL, not only the Prisma schema

The Prisma schema explains intent. The migration folder records what will actually execute.

Open the generated SQL and classify each change:

  • add nullable column;
  • add table or index;
  • backfill data;
  • add constraint;
  • change type;
  • rename or replace;
  • drop column or table;
  • change enum;
  • custom SQL outside Prisma's model.

Schema-level intent can hide a destructive generated operation. A rename may be represented as a drop and create unless the migration is edited and reviewed carefully.

2. Keep development and production workflows separate

Use development commands in development. Use the production deployment path in CI/CD.

Never treat an interactive development command as a safe production rehearsal. Development workflows may assume that resetting or recreating local state is acceptable; production data does not have that property.

Prisma's documentation explicitly separates these workflows. The deployment review should record which command, environment and account executes the migration.

3. Account for the migration-runner transaction model

The generated SQL is executed by a runner. That runner may apply a transaction boundary, use a lock or serialize concurrent deployments.

Ask:

  • Does this migration run inside a transaction?
  • Is custom SQL allowed?
  • Are all files applied in one transaction or individually?
  • Can a migration be marked non-transactional?
  • What happens after partial failure?
  • Are checksums or migration records updated consistently?

Runner behavior matters for concurrent index creation, long backfills, enum changes and partial failures.

4. Do not let CREATE INDEX CONCURRENTLY run inside a transaction

PostgreSQL rejects concurrent index creation inside a transaction block. A migration may look safe in isolation while the runner wraps it automatically.

Verify:

  • a dedicated non-transactional migration path;
  • that no explicit BEGIN surrounds the statement;
  • the index is valid after completion;
  • interrupted builds are detected and cleaned up;
  • application code can tolerate the index being unavailable until it is valid.

The PostgreSQL CREATE INDEX documentation is the primary reference for the transaction restriction and concurrent-build behavior.

5. Split destructive schema changes into expand and contract

Generated changes should not remove fields that the previous application version still uses.

Use:

  1. Expand: add nullable columns or new tables.
  2. Dual-write: update both representations.
  3. Backfill: process existing rows in bounded batches.
  4. Verify: reconcile counts and invalid values.
  5. Contract: add final constraints and switch reads.
  6. Cleanup: remove legacy structures in a later release.

This pattern is especially important for rolling deployments where old and new application instances coexist.

6. Treat backfills as application data migrations

Prisma can manage schema changes, but data movement still requires an operational design.

Define:

  • source and target mapping;
  • stable batch ordering;
  • transaction or commit scope;
  • idempotence;
  • progress checkpoints;
  • retries;
  • failure isolation;
  • row-count reconciliation;
  • what happens when application writes modify a row during the backfill.

One giant UPDATE is not a complete data migration plan merely because it has a WHERE clause.

7. Constraint changes need staged validation

For existing tables:

  • add foreign keys and checks as NOT VALID;
  • reconcile invalid rows;
  • validate in a separate controlled step;
  • add final NOT NULL constraints only after the data is proven complete.

The PostgreSQL ALTER TABLE documentation explains the validation and concurrency options. The operational decision still depends on table size, traffic and lock timeouts.

8. Review enum and type changes carefully

Enum additions, type changes and generated column changes can affect:

  • transaction visibility;
  • old application versions;
  • API serializers;
  • database defaults;
  • function signatures;
  • indexes and constraints.

A migration can commit successfully and still leave the application unable to use the new value or representation.

9. Verify migration history and deployment order

Before deploying:

  • every pending migration has been reviewed;
  • migration files are immutable after review;
  • the target environment is at the expected baseline;
  • no manual production change has created schema drift;
  • failed or baselined migrations have an explicit resolution;
  • the deployment job uses the intended database role;
  • concurrent deployments cannot race.

Migration history is an operational record. It is not proof that each SQL change is safe.

10. Test rollback and forward-fix at the right layer

Prisma records migrations, but application rollback and database rollback are different decisions.

Ask:

  • Can old application code run against the expanded schema?
  • Is the generated migration reversible without data loss?
  • Is a reverse migration available and tested?
  • Would a failed migration leave the history table inconsistent?
  • Should the team stop, revert code, restore, or continue forward with a corrective migration?

A drop cannot be undone by deleting a migration record.

Common false sense of safety

  • “It passed prisma validate.”
  • “It ran on an empty local database.”
  • “The migration is in source control.”
  • “The schema looks backward compatible.”
  • “Prisma uses an advisory lock.”
  • “There are no scanner findings.”

Each statement can be true while a production release still fails because of row volume, lock duration, runner behavior, application compatibility or missing recovery evidence.

Final checklist

  • Generated SQL was reviewed line by line.
  • Destructive and compatibility-changing operations are separated.
  • Development and production commands are clearly distinguished.
  • Runner transaction behavior is known.
  • Concurrent index creation is outside transactions.
  • Backfill is bounded and reconciled.
  • Constraint validation is staged.
  • Old/new application compatibility was tested.
  • Backup, restore and rollback/forward-fix evidence exists.
  • The release was rehearsed on representative data.

If several items are unknown, split the migration. A smaller, observable expand phase is usually safer than approving a generated bundle whose production behavior has not been evidenced.
